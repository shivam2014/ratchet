# T3 Code integration

T3 Code is a harness with a control plane over providers. Its nightly docs do not define a custom agent, plugin, or lifecycle-hook API. Provider behavior comes from the provider instance, and app-owned orchestration is exposed through the T3 MCP server.

## What is supported today

The current T3 thread runs `providerInstanceId: "opencode"` with `opencode-go/deepseek-v4.1-flash`. Ratchet installs at the OpenCode provider layer:

```bash
ratchet install --harness t3 --project --yes
```

That writes `.opencode/plugins/ratchet.js` (or the global OpenCode plugin path) and the Ratchet skill. The adapter maps:

| OpenCode hook | Ratchet event | Behavior |
|---|---|---|
| `execute.before` | `tool.before` | Deny a write or bash call outside the contract |
| `execute.after` | `tool.after` | Run post-write checks and return the failure to the model |

For every T3 thread on this machine, install once at user scope:

```bash
ratchet install --harness t3 --user --yes
```

Then restart T3 Code. The plugin is a no-op outside a repo with `.ratchet/current`, so a global install is safe.

The plugin is safe outside a Ratchet repo. MCP tools and some subagent calls may bypass it, so git and CI remain the authority. With `sandbox.enabled`, the OpenCode 2.x plugin also rewrites a bash command to run under the contract's seatbelt profile; the same MCP and subagent gaps remain.

Prompt guidance reaches T3 threads through the repo's `AGENTS.md`, installed skills, and the contract brief in the prompt. The full Stop gate is not available at this layer. Use the git pre-commit hook and required CI.

## Turn it off

There are three off switches, from softest to hardest.

1. Per repo, recorded. Run `ratchet disable --reason "why"`. The plugin still loads, but every write is allowed and the trail records the reason. Re-enable with `ratchet enable`.
2. Per repo, no CLI needed. Delete `.ratchet/current`. The plugin no-ops when there is no active contract. Use this when the `ratchet` binary itself is broken.
3. Remove the plugin. Run `ratchet uninstall --harness t3 --project` for a project install. For a user install, run `ratchet uninstall --harness t3 --user` from the repo where you installed it, or delete `~/.config/opencode/plugins/ratchet.js`. Restart T3 Code after a user-scope change.

The plugin fails closed. If `ratchet` cannot run, an in-scope write is blocked too. Use switch 2 or 3 in that case.

## Why not a T3 native hook

- T3's public orchestration surface is the authenticated MCP server. It supports thread launch/send/read/wait/interrupt, not pre-tool interception.
- T3's provider adapters normalize provider events internally. There is no public plugin API for prompt or turn events in the nightly docs.
- A T3 controller can run the outer loop through MCP (launch, wait, check, send failures), but it needs an OAuth MCP credential and does not get a pre-tool veto.
- A native T3 provider adapter would be a T3 change, not a Ratchet change.

## Verification

- `npm test` covers the OpenCode adapter with a fake hook context and a real temp repo.
- `ratchet install --harness t3 --project --yes` writes the provider plugin.
- After changing provider config, use **Settings > Providers > Refresh provider status**, then start a new thread. A running thread does not discover a new plugin.
- `ratchet doctor` verifies the installed files.
- A live thread proves the provider loads the plugin. See the proof below.

### Live T3 Code Nightly proof

On 2026-10-21, a T3 project was registered from a repo with the plugin installed, and a thread was launched at the project root on `opencode` / `opencode-go/deepseek-v4.1-flash`. The prompt asked for `src/second.txt` and `outside.txt`. The first write was allowed. The second was denied with `outside.txt is outside scope [src/**]`. `outside.txt` was absent, `ratchet report` showed one allow and one deny, and `ratchet check` passed.

The thread is [Ratchet T3 live guard](t3-thread://v1/mcp:9397e9fd-eceb-4d3d-9023-aa98cdc13b4c). The test repo is `~/t3-nightly-ratchet-test`. The check is still manual because T3 has no test harness for provider loading.

### Live kill switch proof

On 2026-10-21, `ratchet disable --reason "live kill switch test"` was run in the test repo, and a new T3 thread asked for `outside.txt`. The write succeeded. `ratchet report` recorded `ALLOW write ... ratchet disabled: live kill switch test`. `ratchet enable` and `ratchet check` restored the gate.

## Next

A T3 control-plane adapter would add the missing Stop gate for T3-owned threads. It needs:

1. A T3 MCP OAuth credential or the local WebSocket RPC transport.
2. `t3_thread_launch` / `t3_thread_wait` / `t3_thread_read` / `t3_thread_send` around `ratchet check`.
3. A clear limit: pre-tool enforcement still depends on the provider plugin or T3 runtime modes.

Until that exists, T3 is supported at the provider layer, not at the T3-native lifecycle layer.
